Roteiro completo seguindo o roadmap de Computer Science — da linguagem C até System Design. Uma trilha pros iniciantes e uma trilha pra você conduzir como mentor.

Ritmo · 4h/dia Duração · ~12–14 meses 14 fases Idioma · cursos em PT

§Como usar este plano

São duas trilhas paralelas. A trilha do grupo é a ordem das aulas e exercícios que vocês fazem juntos. A trilha do mentor (você) é como se preparar antes pra ensinar e responder dúvidas — está no fim do documento.

Cada fase tem um checkpoint: o que os amigos devem conseguir fazer sozinhos, sem ajuda, antes de avançar. Se não passam, não avança — repete o exercício, não o vídeo.

A regra de ouro

Vídeo não forma mestre — código forma. A cada estrutura ou conceito novo, cada pessoa reimplementa do zero sem olhar. Assistir passivamente cria uma ilusão de domínio que evapora na primeira tela em branco.

Sobre o prazo, com honestidade

4h por dia por mais de um ano é uma maratona. Consistência vale mais que velocidade. Reservem 1 semana de folga/revisão a cada ~2 meses — descanso planejado evita o abandono por exaustão. As durações abaixo assumem dias de estudo de verdade, não dias corridos de calendário.

Estudo e projeto andam juntos

Vocês não esperam o fim pra construir. A partir da Fase 2 (quando já têm hash table) abrem o capstone — o mini-Redis — e cada fase nova destrava uma camada nova dele. O estudo ensina o conceito; a camada do projeto crava ele. Detalhes na Trilha de projeto.

§O dia de 4 horas

Uma estrutura que funciona pra grupo com mentor. Ajustem, mas mantenham os quatro blocos.

0:00
Revisão (20 min). Cada um explica em voz alta o que aprendeu ontem. Quem ensina, fixa.
0:20
Conteúdo novo (90 min). Vídeo da fase + você explicando e abrindo espaço pra dúvida.
1:50
Codar junto (60 min). Implementar ao vivo, todos digitando, não só assistindo.
2:50
Prática individual (60 min). Cada um sozinho, refazendo sem cola e resolvendo exercícios.
3:50
Checkpoint (10 min). Conferir o que travou e definir o ponto de partida de amanhã.

Tipos de dados avançados — fechando o roadmap

Destrava ao longo das Fases 3–6
esforço ~3–4 sem (incremental)

Esta é a camada que faz o projeto cravar os nós do roadmap que sobrariam de fora. Cada comando novo do seu DB é, na prática, uma estrutura ou algoritmo do roadmap em uso real — exatamente como o Redis de verdade faz.

  • Sorted Set (ZADD/ZRANGE) sobre uma Skip List — exercita skip list e ordenação por score.
  • Autocomplete de chaves por prefixo sobre uma Trie / PATRICIA — exercita árvores digitais.
  • KEYS pattern e SCAN MATCH com glob — casamento de padrões: força bruta → KMP / Boyer-Moore; o glob com */? é backtracking.
  • Busca fuzzy (“você quis dizer…”) por distância de edição — Programação Dinâmica em produção.
  • Bitmaps (SETBIT/BITCOUNT) — operadores bit a bit; e a serialização binária do C4 te dá endianness.
  • HyperLogLog e Bloom filter (PFADD/PFCOUNT) — probabilidade, combinatória e hashing aplicados.
  • Geo (GEOADD/GEOSEARCH) sobre uma K-D Tree — busca espacial; e INCRBYFLOAT exercita ponto flutuante.
  • Opcional/ápice: módulo de grafo com menor caminho (Dijkstra/BFS) — fecha a parte de grafos do roadmap dentro do projeto.

Por que isso importa

Quase ninguém consegue dizer “implementei skip list, trie, bloom filter, WAL, replicação e protocolo de rede — tudo no mesmo projeto, em C”. Quando os quatro chegarem ao fim, cada um terá tocado todas as áreas do roadmap com as próprias mãos. Isso é o que separa “fiz um curso” de “sei construir”.

1 · O esqueleto de um programa

Todo programa em C tem a mesma espinha: você inclui bibliotecas, declara a função main (o ponto de partida) e termina cada comando com ponto e vírgula.

#include <stdio.h>      // biblioteca de entrada e saída (printf, scanf)

int main() {            // a execução SEMPRE começa aqui
    printf("Olá!\n");   // cada comando termina com ;
    return 0;           // 0 = "terminou tudo certo"
}

As 4 peças que se repetem sempre

#include traz ferramentas prontas. { } delimitam blocos. ; encerra cada comando (esquecer o ; é o erro nº1 do iniciante). return 0; avisa o sistema que deu tudo certo.

2 · Variáveis e tipos

Uma variável é uma “caixa” com nome que guarda um valor. Em C você precisa dizer o tipo da caixa antes de usar.

int    idade = 25;        // número inteiro
float  altura = 1.75;     // número com vírgula (precisão simples)
double preco = 1999.90;   // número com vírgula (mais preciso)
char   letra = 'A';       // UM caractere — aspas SIMPLES
const double PI = 3.14159; // const = não pode mudar depois

Aspas fazem diferença

'A' (aspas simples) é UM caractere. "A" (aspas duplas) é uma string. Trocar isso é um erro comum.

3 · Entrada e saída — printf e scanf

printf mostra na tela; scanf lê o que o usuário digita. Os “%” são marcadores que dizem o tipo do dado.

int idade;
printf("Quantos anos voce tem? ");
scanf("%d", &idade);              // & = "endereco de" (scanf precisa dele!)
printf("Voce tem %d anos.\n", idade);

// vários de uma vez:
printf("Nome: %s | Idade: %d | Altura: %.2f\n", nome, idade, altura);

O & no scanf e os atalhos

No scanf, variáveis comuns levam & antes (ex.: &idade) — é onde o valor vai ser guardado. Exceção: string (vetor de char) NÃO leva &. Atalhos úteis: \n pula linha, \t dá um tab, %.2f mostra 2 casas decimais.

4 · Operadores

// Aritméticos
a + b   a - b   a * b   a / b   a % b   // % = resto da divisão

// Atribuição (atalhos)
x += 5;   // x = x + 5      x -= 2;   x *= 3;   x /= 2;

// Comparação (resultam em verdadeiro/falso)
a == b   // IGUAL  (atencao: == e nao =)
a != b   // diferente
a > b    a < b    a >= b    a <= b

// Lógicos
a && b   // E   (os dois verdadeiros)
a || b   // OU  (pelo menos um)
!a       // NAO (inverte)

// Incremento / decremento
i++;   // i = i + 1        i--;   // i = i - 1

A pegadinha eterna: = vs ==

= atribui (coloca um valor na variável). == compara. Escrever if (x = 5) sem querer é um bug clássico — sempre dá “verdadeiro” e muda o x. Para comparar, é sempre ==.

Divisão de inteiros engana

7 / 2 dá 3 (não 3.5!), porque os dois são int. Para ter casas decimais, um deles precisa ser float/double: 7.0 / 2 dá 3.5.

5 · Condicionais — if, else, switch

if (idade >= 18) {
    printf("Maior de idade\n");
} else if (idade >= 13) {
    printf("Adolescente\n");
} else {
    printf("Crianca\n");
}

// switch: quando você compara UMA variável com vários valores fixos
switch (opcao) {
    case 1: printf("Um\n");   break;   // break = sai do switch
    case 2: printf("Dois\n"); break;
    default: printf("Invalido\n");     // se nenhum bateu
}

Não esqueça o break

Sem break, o switch “escorrega” e executa os próximos case também. Quase sempre você quer o break em cada caso.

6 · Laços (loops)

Servem pra repetir. while repete enquanto uma condição for verdadeira; for é o mesmo, mas com contador embutido; do-while roda pelo menos uma vez.

// for — quando você sabe quantas vezes (o mais usado)
for (int i = 0; i < 5; i++) {
    printf("%d ", i);     // imprime: 0 1 2 3 4
}

// while — repete enquanto a condição for verdadeira
int n = 10;
while (n > 0) {
    printf("%d ", n);
    n--;                  // CUIDADO: se esquecer isso, loop infinito!
}

// do-while — executa, depois testa (roda no minimo 1 vez)
do {
    printf("Pelo menos uma vez\n");
} while (0);

// break sai do laço; continue pula pra próxima volta
for (int i = 0; i < 10; i++) {
    if (i == 5) break;       // para tudo no 5
    if (i % 2 == 0) continue; // pula os pares
    printf("%d ", i);         // imprime: 1 3
}

Loop infinito

Todo while precisa de algo que aproxime do fim (mudar a variável da condição). Esqueceu o n--? O programa trava repetindo pra sempre. É a pegadinha mais comum de laço.

7 · Vetores (arrays)

Um vetor guarda vários valores do mesmo tipo numa fila. O índice começa em 0 — sempre.

int notas[5] = {7, 8, 9, 10, 6};   // 5 posições: índices 0 a 4
printf("%d\n", notas[0]);          // 7  (a PRIMEIRA é o índice 0)
notas[2] = 5;                      // muda a terceira posição

// percorrer com for:
int soma = 0;
for (int i = 0; i < 5; i++) {
    soma += notas[i];
}

Estourar o vetor não dá erro… na hora

Um int v[5] vai de v[0] a v[4]. Acessar v[5] é “fora dos limites” — C deixa, mas você lê/escreve numa memória que não é sua. Vira bug bizarro ou crash. Sempre respeite 0 até tamanho-1.

8 · Matrizes (vetores 2D)

Uma matriz é um vetor de vetores — tipo uma tabela com linhas e colunas.

int tabela[2][3] = {
    {1, 2, 3},    // linha 0
    {4, 5, 6}     // linha 1
};
printf("%d\n", tabela[1][2]);   // 6  (linha 1, coluna 2)

// percorrer: um for dentro do outro
for (int i = 0; i < 2; i++) {       // linhas
    for (int j = 0; j < 3; j++) {   // colunas
        printf("%d ", tabela[i][j]);
    }
    printf("\n");
}

9 · Structs (registros)

Uma struct junta vários campos relacionados num só “tipo” seu. Perfeito pra representar coisas do mundo real (um lead, um cliente, um ponto…).

struct Lead {
    char  nome[50];
    int   idade;
    double valor;
};

struct Lead l1;                 // cria um
strcpy(l1.nome, "Caio");        // acessa campo com ponto (.)
l1.idade = 25;
l1.valor = 1999.90;
printf("%s tem %d anos\n", l1.nome, l1.idade);

Liga com o trabalho

Struct é a base do que você já faz em C# com classes/DTOs. Aqui é a versão crua: um agrupamento de dados. No projeto capstone, cada entrada do banco vai ser, no fundo, uma struct.

10 · Funções e procedimentos

Função é um bloco de código com nome, que você chama quando quiser. Evita repetir e organiza tudo. Tem tipo de retorno, nome e parâmetros.

// função que RETORNA um valor
int somar(int a, int b) {
    return a + b;
}

// "procedimento": não retorna nada -> void
void saudar(char nome[]) {
    printf("Ola, %s!\n", nome);
}

int main() {
    int r = somar(3, 4);   // r = 7
    saudar("Caio");
    return 0;
}

Passagem por valor

Por padrão, C passa uma cópia do argumento. Mudar o parâmetro dentro da função não muda a variável original lá fora. Pra mudar de verdade, você usa ponteiros (próximo tópico). Esse é o link direto pra Fase 1.

Protótipo

Se a função aparece depois do main, declare o protótipo no topo: int somar(int, int); — é só avisar ao compilador que ela existe.

11 · Ponteiros — o muro mais alto

Esse é o conceito que mais trava iniciante, então vai devagar. Toda variável mora num endereço na memória (tipo o número de uma casa). Um ponteiro é uma variável que guarda um endereço — ou seja, “aponta” pra onde outra variável mora.

A analogia da casa

Endereço = o número da casa.   &x = “me dá o endereço da casa do x”.   *p = “abre a casa que o p aponta e me mostra o que tem dentro”.

int x = 10;
int *p = &x;     // p guarda o ENDEREÇO de x  (& = "endereço de")

printf("%d\n", x);    // 10  -> o valor
printf("%p\n", p);    // 0x...  -> o endereço (a "casa")
printf("%d\n", *p);   // 10  -> o valor NA casa que p aponta (* = "conteúdo de")

*p = 20;         // muda o conteúdo da casa -> muda o PRÓPRIO x!
printf("%d\n", x);    // 20

Agora o passo que faltava nas funções: passar o endereço pra função poder alterar a variável original.

void dobrar(int *n) {     // recebe um ponteiro
    *n = *n * 2;          // altera o conteúdo lá na origem
}

int main() {
    int valor = 5;
    dobrar(&valor);       // passa o ENDEREÇO de valor
    printf("%d\n", valor); // 10  -> mudou de verdade!
}

Resumo dos dois símbolos

& pega o endereço de uma variável. * (na hora de usar) abre o ponteiro e mexe no valor que ele aponta. Decore: “& = onde mora, * = o que tem dentro”.

12 · Alocação dinâmica de memória

Até aqui o tamanho de tudo era fixo (int v[5]). Mas e quando você só descobre o tamanho durante a execução (ex.: o usuário diz quantos itens)? Aí você pede memória na hora com malloc — e depois devolve com free.

#include <stdlib.h>     // malloc, free

int n;
printf("Quantos numeros? ");
scanf("%d", &n);

// pede memória pra n inteiros (na "heap")
int *v = malloc(n * sizeof(int));
if (v == NULL) { return 1; }   // sempre cheque se deu certo

for (int i = 0; i < n; i++) v[i] = i * 10;

free(v);     // DEVOLVE a memória. Esquecer = vazamento (memory leak)
v = NULL;    // boa prática: evita usar um ponteiro "morto"

A regra de ouro da memória

Todo malloc precisa de um free correspondente. Esqueceu o free? O programa vai comendo memória (leak). Usou depois do free? Bug grave (use-after-free). Esse cuidado é exatamente o que a Camada C2 do projeto vai cobrar de vocês.

Por que isso é o pré-requisito de tudo

Listas, árvores, hash tables — toda estrutura de dados “cresce” em tempo de execução, e isso só é possível com ponteiros + alocação dinâmica. É por isso que o plano insiste: não pulem ponteiros e memória. Sem isso, a Fase 2 em diante não anda.

13 · Projeto com vários arquivos

Programas reais não vivem num arquivo só. Você separa em .h (o que existe — as “assinaturas”) e .c (como funciona — o código).

// ---------- matematica.h ----------
#ifndef MATEMATICA_H      // include guard: evita incluir 2x
#define MATEMATICA_H
int somar(int a, int b);  // só a assinatura (protótipo)
#endif

// ---------- matematica.c ----------
#include "matematica.h"
int somar(int a, int b) { return a + b; }   // a implementação

// ---------- main.c ----------
#include <stdio.h>
#include "matematica.h"   // aspas " " = arquivo seu (< > = do sistema)
int main() { printf("%d\n", somar(2, 3)); return 0; }

Include guard

O trio #ifndef / #define / #endif garante que o cabeçalho seja incluído uma única vez, mesmo se vários arquivos o pedirem. Sem ele, dá erro de “redefinição”.

14 · Conversão de tipos (casting) e sizeof

Às vezes você precisa forçar um tipo a virar outro. E sizeof diz quantos bytes algo ocupa.

int a = 7, b = 2;
double r = (double)a / b;     // 3.5 — o (double) força a conta a virar decimal
printf("%zu\n", sizeof(int)); // 4 (em geral) — tamanho do tipo em bytes

15 · Operador ternário

Um if/else enxuto, em uma linha. Formato: condição ? valor_se_verdadeiro : valor_se_falso.

int idade = 20;
char *tipo = (idade >= 18) ? "adulto" : "menor";   // escolhe na hora
int maior = (a > b) ? a : b;                        // máximo entre dois

16 · Escopo, static e const

Variável declarada dentro de uma função (local) só existe ali. Global (fora de tudo) existe no programa inteiro. static faz uma local lembrar o valor entre chamadas. const trava o valor.

int contador() {
    static int n = 0;   // não zera a cada chamada — lembra o valor
    return ++n;         // 1, 2, 3, ... a cada vez que chamar
}
const double TAXA = 0.05;   // não pode ser alterado depois

17 · Recursão

Uma função que chama a si mesma. Precisa SEMPRE de um caso base (a condição de parada), senão vira loop infinito que estoura a memória (stack overflow).

int fatorial(int n) {
    if (n <= 1) return 1;          // caso base: para aqui
    return n * fatorial(n - 1);    // chama a si mesma, menor
}
// fatorial(4) = 4*3*2*1 = 24

Por que importa

Recursão é o jeito natural de percorrer árvores e resolver “dividir pra conquistar” (Merge Sort, Quick Sort). É um músculo que você vai usar muito da Fase 3 em diante.

18 · enum, typedef e union

enum Status { ATIVO, INATIVO, PENDENTE };   // vira 0, 1, 2 — nomes pra inteiros
enum Status s = ATIVO;

typedef struct {                            // typedef = apelido de tipo
    char nome[50];
    int  idade;
} Pessoa;
Pessoa p;        // agora não precisa escrever "struct" toda hora

union Valor {    // union: todos os campos dividem o MESMO espaço
    int   inteiro;
    float decimal;
};               // útil pra economizar memória quando só um é usado por vez

19 · Pré-processador e macros (#define)

O #define faz uma “troca de texto” antes de compilar. Serve pra constantes e pequenas macros.

#define PI 3.14159
#define AREA(r) (PI * (r) * (r))    // macro com argumento

double a = AREA(5);   // o compilador troca por (3.14159 * (5) * (5))

⚠ Parênteses são obrigatórios

Em macro, embrulhe cada argumento em parênteses: (r). Sem isso, AREA(2+1) vira conta errada. Macro não é função — é substituição literal de texto.

20 · Operadores bit a bit

Mexem nos bits diretamente. Parecem exóticos agora, mas são a base de bitmaps, flags e compressão.

a & b    // AND  — 1 só onde os dois são 1
a | b    // OR   — 1 onde pelo menos um é 1
a ^ b    // XOR  — 1 onde são diferentes
~a       // NOT  — inverte todos os bits
a << 2   // desloca p/ esquerda  (= multiplica por 4)
a >> 1   // desloca p/ direita    (= divide por 2)

21 · Ponteiro de função

Dá pra guardar uma função dentro de uma variável e chamá-la depois. Parece estranho, mas é o coração de como C faz “polimorfismo” e tabelas de comando.

int somar(int a, int b) { return a + b; }

int (*op)(int, int) = somar;   // op aponta para a função somar
printf("%d\n", op(2, 3));      // 5 — chama através do ponteiro

22 · Arquivos — ler e escrever em disco

Até aqui tudo morria quando o programa fechava. Com arquivos, os dados persistem.

#include <stdio.h>

FILE *f = fopen("dados.txt", "w");   // "w" escreve, "r" lê, "a" anexa
if (f != NULL) {

f = fopen("dados.txt", "r");
if (f) { fgets(linha, sizeof linha, f); fclose(f); }

Strings em C — o caderno

Tudo o que vocês precisam sobre strings: o conceito, os comandos, as funções e as pegadinhas. Cole no caderno, deixe aberto enquanto codam.

A ideia que explica tudo: o \0

Em C não existe um tipo “string”. Uma string é só um vetor de char que termina num caractere especial: o \0 (byte zero, “null terminator”). Toda função de string para de trabalhar quando encontra o \0. Entendeu isso, entendeu 90% dos bugs.

1 · Declaração e inicialização

char a[] = "C";          // tamanho 2: 'C' + '\0' (o compilador conta)
char b[20] = "Plaenge";  // reserva 20, usa 8, sobra espaço pra crescer
char c[4] = "abc";       // OK: a,b,c,\0 — exatamente 4
char d[3] = "abc";       // BUG: não cabe o '\0'!
char *e = "texto";       // ponteiro p/ string LITERAL (não pode alterar)

Vetor char[] vs ponteiro char*

char s[] = "oi" cria uma cópia que você pode alterar. char *s = "oi" aponta pra um literal somente-leitura — tentar mudar trava o programa. Pra texto que muda, use vetor.

2 · Acentos no console — setlocale

É o que aparece no topo do código da sua aula. Sem isso, ç, ã e á saem quebrados no terminal do Windows.

#include <locale.h>
setlocale(LC_ALL, "Portuguese");   // habilita acentuação

3 · Entrada — lendo strings

scanf("%s", s)stdio.h

Lê uma palavra (para no primeiro espaço). Repare: com vetor de char não se usa &.

char nome[30];
scanf("%s", nome);   // digita "João Silva" -> guarda só "João"
fgets(s, n, stdin)stdio.h

Lê uma linha inteira com segurança (limita o tamanho). É o jeito recomendado. Inclui o \n no fim — às vezes você quer remover.

char linha[100];
fgets(linha, sizeof linha, stdin);
linha[strcspn(linha, "\n")] = '\0';   // tira o \n do fim
gets(s) ❌ PROIBIDOstdio.h

O Pietro mostra, mas é pra você nunca usar. Não limita o tamanho → estoura o buffer → falha de segurança clássica. Foi removido do C11. Use sempre fgets no lugar.

char s[10];
gets(s);   // se o usuário digitar 50 chars, corrompe a memória

4 · Saída — imprimindo strings

puts(s)stdio.h

Imprime a string e já pula linha (adiciona \n sozinho). Mais simples que printf quando é só texto puro.

puts("Antes do strcat:");   // imprime e quebra a linha
saídaAntes do strcat:
printf("%s", s)stdio.h

Imprime com formatação. Use quando precisa misturar texto e variáveis.

printf("str1: %s\n", s1);   // %s = encaixa a string aqui
putchar(c)stdio.h

Imprime um único caractere. Útil ao percorrer a string letra a letra.

putchar('A');   // imprime: A

5 · Percorrer caractere a caractere

O padrão mais importante: ande pelo vetor até bater no \0.

char s[] = "C é vida";
for (int i = 0; s[i] != '\0'; i++) {   // para no terminador
    putchar(s[i]);
}

6 · Biblioteca string.h — as funções

strlen(s)string.h

Tamanho lógico da string — conta até o \0, sem incluí-lo. Diferente de sizeof, que é o tamanho do vetor.

char s[] = "Plaenge";
size_t n = strlen(s);   // 7  (P-l-a-e-n-g-e)

3 · Dynamic Array a fundo

Um vetor dinâmico (dynamic array) é um array comum que cresce sozinho quando enche. Por baixo ele continua sendo um bloco contíguo de memória — o mesmo array de sempre — só que guarda dois números: quantos itens já tem (size) e quantos cabem no bloco atual (capacity). Pensa num ônibus: enquanto tem assento vago, sobe gente; quando lota, você troca por um do dobro do tamanho e passa todo mundo pro novo. O List<T> do C# e o std::vector do C++ são isso — em C, você monta na mão com malloc/realloc.

Quando usar / quando NÃO usar

USE quando: quer acesso por índice O(1), precisa iterar rápido (memória contígua é amiga do cache da CPU), não sabe o tamanho final e a maioria das inserções é no fim.

NÃO use quando: vai inserir/remover muito no meio (empurra todo mundo, O(n)); precisa de ponteiros estáveis pros elementos (o realloc pode mover o bloco e seus ponteiros viram lixo); ou já sabe o tamanho exato (aí um malloc único basta).

O push é O(1) amortizado, não O(1) sempre: quase sempre só escreve numa posição livre (O(1)); de vez em quando enche e copia tudo pro bloco novo (O(n)). Como a capacidade dobra, essas cópias ficam raras — em n inserções o custo total dá O(n), ou seja, O(1) por inserção na média. (Isso é a Análise Amortizada, tópico 6 daqui.)

#include <stdlib.h>   // malloc, realloc, free
#include <stddef.h>   // size_t

// A struct guarda 3 coisas. Os dois números (size e capacity) são o segredo.
typedef struct {
    int    *data;       // ponteiro pro bloco contíguo na heap
    size_t  size;       // quantos elementos ESTÃO em uso
    size_t  capacity;   // quantos CABEM antes de precisar crescer
} DynArray;

// Começa vazio: nenhum bloco, nenhum item.
void da_init(DynArray *a) {
    a->data = NULL;     // ainda não pedimos memória nenhuma
    a->size = 0;
    a->capacity = 0;
}

// Garante espaço p/ +1 item. É AQUI que mora a expansão geométrica.
static int da_grow(DynArray *a) {
    if (a->size < a->capacity) return 1;          // já tem folga: nada a fazer
    size_t nova = (a->capacity == 0) ? 4 : a->capacity * 2;  // dobra (ou começa em 4)
    int *novo = realloc(a->data, nova * sizeof(int));       // pede um bloco maior
    if (novo == NULL) return 0;                  // falhou: o bloco antigo segue válido
    a->data = novo;        // realloc pode ter MOVIDO tudo -> atualiza o ponteiro
    a->capacity = nova;
    return 1;
}

// Adiciona no fim. Custo O(1) amortizado (raramente realoca).
int da_push(DynArray *a, int valor) {
    if (!da_grow(a)) return 0;     // garante espaço (pode realocar/copiar)
    a->data[a->size] = valor;       // escreve na 1ª posição livre
    a->size++;                      // agora tem 1 a mais
    return 1;
}

int da_get(DynArray *a, size_t i) {
    return a->data[i];   // O(1) puro (sem checar limite aqui, p/ ficar curto)
}

void da_free(DynArray *a) {
    free(a->data);      // devolve o bloco ao sistema
    a->data = NULL;     // evita ponteiro pendurado (dangling)
    a->size = a->capacity = 0;
}
// Uso: DynArray a; da_init(&a); da_push(&a,10); int x=da_get(&a,0); da_free(&a);

⚠ Erro nº1: ponteiro pendurado depois de crescer

Você guarda um ponteiro (ou o endereço de um elemento) e depois dá push. Se nesse push o array encher, o realloc pode mover o bloco inteiro de lugar — e seu ponteiro antigo passa a apontar pra lixo (use-after-free). Regra de ouro: nunca segure ponteiro pra dentro do vetor atravessando um push; guarde o índice e refaça a->data[i]. Bônus: confundir size com capacity (iterar até capacity lê lixo) e não checar se o realloc deu NULL (vaza o bloco antigo).

Direto no projeto (mini-Redis)

É a espinha dorsal do store. A struct {data, size, capacity} vira (a) a string dinâmica estilo sds — buffer de char que cresce no append, usado pra guardar valores e montar respostas; e (b) o buffer de argumentos ao parsear RESP (SET chave valor → vetor de tokens que cresce). Encaixa na Camada C0 (estruturas base) e reaparece no protocolo da C3.

  1. (Fácil) Implemente int da_pop(DynArray *a): remove o último e devolve o valor. Precisa realocar? O que muda em size?
  2. (Médio) Encolhimento: quando size <= capacity/4, corte a capacity pela metade. Por que disparar em /4 e não em /2?
  3. (Difícil) da_insert(a, i, valor) inserindo no meio (empurra pra direita). Qual o Big-O? Em que sentido você percorre o array?

Gabarito

1. if(a->size==0){/*erro*/} a->size--; return a->data[a->size]; — só decrementa size; não precisa realocar.

2. Disparar em /4 cria histerese (folga). Se cortasse já em /2, um padrão push,pop,push,pop… na fronteira realocaria a cada operação (thrashing, O(n) repetido). Cortando só em /4 e voltando pra /2, o amortizado continua O(1).

3. O(n): empurra os (size-i) elementos. Percorra de trás pra frente pra não sobrescrever: for(size_t j=a->size; j>i; j--) a->data[j]=a->data[j-1]; depois a->data[i]=valor; a->size++; (com da_grow antes).

Anki

P: Diferença entre size e capacity? → R: size = itens em uso; capacity = quantos cabem antes de realocar.

P: Por que push é O(1) amortizado e não O(1) sempre? → R: às vezes enche e copia tudo (O(n)), mas como dobra, o total de n pushes é O(n).

P: Por que dobrar (geométrico) e não +1 (aritmético)? → R: +1 daria O(n²) total; dobrar deixa as cópias raras → O(1) amortizado.

P: Bug clássico de guardar ponteiro pra elemento e dar push? → R: realloc pode mover o bloco e o ponteiro vira dangling; guarde o índice.

P: Em C, qual função cresce o bloco preservando o conteúdo? → R: realloc (cheque se não retornou NULL).

7 · Deque (fila de duas pontas)

Um deque (double-ended queue, fala-se "déqui") é uma fila em que você adiciona e remove pelas duas pontas — frente e trás — tudo em O(1). É o "canivete suíço" das estruturas lineares: ele generaliza a pilha (mexe só numa ponta) e a fila (entra atrás, sai na frente). Analogia: uma fila de pessoas onde dá pra entrar e sair tanto pela frente quanto pelo fundo.

Quando usar / quando NÃO usar

USE em: janela deslizante (sliding window), undo/redo, work-stealing de threads, e qualquer buffer onde você precisa das duas pontas.

NÃO use quando: só precisa de uma ponta (uma pilha ou fila é mais simples e enxuta), ou quando precisa de acesso por índice no meio com frequência (na versão de lista ligada isso é O(n)).

OperaçãoTempo (Big-O)Espaço
push_front / push_backO(1)O(1)
pop_front / pop_backO(1)O(1)
peek_front / peek_backO(1)O(1)
Acesso por índice (no meio)O(n) (lista ligada)O(1)
Memória totalO(n)+2 ponteiros por nó

Existem duas implementações clássicas: lista duplamente ligada (a daqui — todas as pontas O(1), mas gasta 2 ponteiros por nó e não tem índice O(1)) e buffer circular (array com início/fim que "dão a volta" — índice O(1) e cache-friendly, mas capacidade fixa ou com realloc). Veja o exercício 2.

#include <stdlib.h>
#include <stddef.h>

// Cada nó aponta pro anterior E pro próximo (por isso "duplamente ligada").
typedef struct Node {
    int           val;
    struct Node  *prev, *next;
} Node;

typedef struct {
    Node  *head, *tail;   // as duas pontas
    size_t size;
} Deque;

void dq_init(Deque *d) { d->head = d->tail = NULL; d->size = 0; }

// Adiciona na FRENTE.
int dq_push_front(Deque *d, int v) {
    Node *n = malloc(sizeof(Node));
    if (!n) return 0;
    n->val = v; n->prev = NULL; n->next = d->head;
    if (d->head) d->head->prev = n;   // liga o antigo 1º de volta no novo
    else         d->tail = n;        // lista estava VAZIA -> novo é head e tail
    d->head = n; d->size++;
    return 1;
}

// Adiciona ATRÁS (espelho exato do push_front).
int dq_push_back(Deque *d, int v) {
    Node *n = malloc(sizeof(Node));
    if (!n) return 0;
    n->val = v; n->next = NULL; n->prev = d->tail;
    if (d->tail) d->tail->next = n;
    else         d->head = n;        // estava vazia
    d->tail = n; d->size++;
    return 1;
}

// Remove da FRENTE. Devolve 0 se vazia; o valor sai por *out.
int dq_pop_front(Deque *d, int *out) {
    if (!d->head) return 0;          // vazia
    Node *n = d->head; *out = n->val;
    d->head = n->next;
    if (d->head) d->head->prev = NULL; // novo 1º não tem anterior
    else         d->tail = NULL;      // removeu o ÚLTIMO -> lista ficou vazia
    free(n); d->size--;
    return 1;
}

// Remove ATRÁS (espelho do pop_front).
int dq_pop_back(Deque *d, int *out) {
    if (!d->tail) return 0;
    Node *n = d->tail; *out = n->val;
    d->tail = n->prev;
    if (d->tail) d->tail->next = NULL;
    else         d->head = NULL;
    free(n); d->size--;
    return 1;
}

void dq_free(Deque *d) {
    Node *cur = d->head;
    while (cur) { Node *nx = cur->next; free(cur); cur = nx; } // libera nó a nó
    d->head = d->tail = NULL; d->size = 0;
}

⚠ Erro nº1: esquecer um dos casos de borda (lista vazia / único nó)

Numa lista duplamente ligada todo insert/remove mexe em dois ponteiros (prev e next) — esquecer um deixa a lista corrompida. E os dois casos que mais derrubam: inserir na lista vazia (precisa setar head E tail) e remover o último nó (a outra ponta tem que virar NULL, senão fica apontando pra memória já liberada). Sempre teste com 0 e 1 elemento.

Direto no projeto (mini-Redis)

O deque é literalmente o tipo List do Redis (LPUSH/RPUSH/LPOP/RPOP = push/pop nas duas pontas) — entra na Camada C8. E a lista duplamente ligada é metade do cache LRU da Camada C1: a lista mantém a ordem de uso (o mais recente na frente, o "candidato a despejo" atrás) e o hash dá o O(1) pra achar o nó.

  1. (Fácil) Implemente dq_peek_front e dq_peek_back (olham sem remover).
  2. (Médio) Refaça o deque como buffer circular de capacidade fixa (array + índices head/tail que dão a volta com %). Por que assim você ganha índice O(1) e zero malloc por operação?
  3. (Difícil) Sliding window maximum: dado um array e uma janela k, devolva o máximo de cada janela em O(n) usando um deque monotônico (guarda índices em ordem decrescente de valor). É o aperitivo do tópico "Monotonic Stack/Queue".

Gabarito

1. int dq_peek_front(Deque *d,int *out){ if(!d->head) return 0; *out=d->head->val; return 1; } — e o back usa d->tail.

2. Num array de tamanho cap, guarde head e count. push_back escreve em (head+count)%cap; push_front em head=(head-1+cap)%cap. Como tudo vive num bloco contíguo já alocado, não há malloc/free por operação (mais rápido e cache-friendly) e o elemento i está em (head+i)%cap → índice O(1). O preço é a capacidade fixa (ou crescer com realloc + recolocação).

3. Percorra o array uma vez. Para cada i: remova de trás do deque todos os índices cujo valor é <= arr[i] (nunca mais serão máximo) e dê push_back(i). Remova da frente o índice que saiu da janela (<= i-k). O máximo da janela é sempre arr[deque.front]. Cada índice entra e sai uma vez → O(n).

Anki

P: O que um deque generaliza? → R: pilha (1 ponta) e fila (entra atrás, sai na frente) — ele faz as duas pontas em O(1).

P: Duas implementações clássicas e o trade-off? → R: lista duplamente ligada (todas as pontas O(1), sem índice O(1)) e buffer circular (índice O(1), cache-friendly, capacidade fixa).

P: Por que o pop do último nó é perigoso? → R: a outra ponta precisa virar NULL, senão aponta pra memória liberada.

P: Qual tipo do Redis é um deque? → R: List (LPUSH/RPUSH/LPOP/RPOP).

P: Custo do sliding-window-max com deque monotônico? → R: O(n) — cada índice entra e sai uma vez.

9 · Hash Table avançado — open addressing

A tabela hash básica resolve colisão com encadeamento (uma listinha pendurada em cada balde). O open addressing (endereçamento aberto) faz o contrário: guarda tudo dentro do próprio array. Se o balde calculado já está ocupado, ele procura o próximo livre — isso se chama probing (sondagem). Analogia: estacionamento de shopping. Sua vaga "natural" está ocupada? Você anda até achar a próxima livre. Pra sair (buscar), você refaz o mesmo caminho.

Quando usar / quando NÃO usar

USE quando: quer velocidade bruta e cache-friendliness (tudo num bloco contíguo, zero ponteiros pulando pela memória) e memória apertada (sem o custo dos nós de lista).

NÃO use quando: o fator de carga vai passar de ~0,7 (aí formam-se clusters e tudo degrada pra O(n)), ou quando há muitos deletes (precisa de tombstones, que poluem a tabela com o tempo).

#include <stdlib.h>
#include <stddef.h>

// Cada slot tem 3 estados. calloc zera tudo, então EMPTY tem que ser 0.
typedef enum { EMPTY = 0, USED, DELETED } State;
typedef struct { int key, val; State state; } Slot;
typedef struct { Slot *slots; size_t cap, size; } HMap;

// Espalha a chave pela tabela. (Em produção use um hash melhor, ex. FNV-1a.)
static size_t hsh(int key, size_t cap) {
    return ((size_t)(unsigned)key * 2654435761u) % cap;
}

void hm_init(HMap *h, size_t cap) {
    h->cap = cap; h->size = 0;
    h->slots = calloc(cap, sizeof(Slot));  // zera -> todos EMPTY
}

static void hm_resize(HMap *h, size_t newcap);  // declarado antes de usar

// Insere ou atualiza. Cresce quando passa de ~70% de ocupação.
int hm_put(HMap *h, int key, int val) {
    if ((h->size + 1) * 10 >= h->cap * 7) hm_resize(h, h->cap * 2);
    size_t i = hsh(key, h->cap);
    size_t first_del = h->cap;          // guarda o 1º tombstone p/ reaproveitar
    for (size_t step = 0; step < h->cap; step++) {
        size_t pos = (i + step) % h->cap;            // sondagem linear (dá a volta)
        if (h->slots[pos].state == USED) {
            if (h->slots[pos].key == key) { h->slots[pos].val = val; return 1; } // já existe
        } else if (h->slots[pos].state == DELETED) {
            if (first_del == h->cap) first_del = pos;  // anota e segue sondando
        } else {                                       // EMPTY: a chave não está aqui
            size_t put = (first_del != h->cap) ? first_del : pos; // reusa tombstone se houver
            h->slots[put].key = key; h->slots[put].val = val;
            h->slots[put].state = USED; h->size++;
            return 1;
        }
    }
    return 0;  // tabela cheia (não ocorre por causa do resize)
}

// Busca. Para num EMPTY (não existe), mas PULA tombstones.
int hm_get(HMap *h, int key, int *out) {
    size_t i = hsh(key, h->cap);
    for (size_t step = 0; step < h->cap; step++) {
        size_t pos = (i + step) % h->cap;
        if (h->slots[pos].state == EMPTY) return 0;   // buraco real -> acabou a cadeia
        if (h->slots[pos].state == USED && h->slots[pos].key == key) { *out = h->slots[pos].val; return 1; }
        // DELETED: NÃO pare aqui — a chave pode estar adiante
    }
    return 0;
}

// Remove deixando TOMBSTONE (DELETED), nunca EMPTY — senão quebra a busca.
int hm_del(HMap *h, int key) {
    size_t i = hsh(key, h->cap);
    for (size_t step = 0; step < h->cap; step++) {
        size_t pos = (i + step) % h->cap;
        if (h->slots[pos].state == EMPTY) return 0;
        if (h->slots[pos].state == USED && h->slots[pos].key == key) {
            h->slots[pos].state = DELETED; h->size--;
            return 1;
        }
    }
    return 0;
}

// Dobra e re-insere tudo (rehash). Os tombstones somem nessa faxina.
static void hm_resize(HMap *h, size_t newcap) {
    Slot  *old = h->slots; size_t oldcap = h->cap;
    h->slots = calloc(newcap, sizeof(Slot));
    h->cap = newcap; h->size = 0;
    for (size_t k = 0; k < oldcap; k++)
        if (old[k].state == USED) hm_put(h, old[k].key, old[k].val);
    free(old);
}

⚠ Erro nº1: apagar virando EMPTY em vez de tombstone

Se ao remover você marcar o slot como EMPTY, você fura a cadeia de sondagem: a busca por uma chave que estava "depois" do buraco vai parar nele e dizer "não existe" — mesmo a chave estando lá. Por isso DELETE marca DELETED (tombstone) e a busca pula tombstones, só parando em EMPTY. O outro vilão é o fator de carga alto: passou de ~0,7 e os clusters fazem tudo virar O(n) — por isso o resize não é opcional.

Direto no projeto (mini-Redis)

A tabela hash é o coração do store — a Camada C0 (o GET/SET/DEL são put/get/del nela). O Redis de verdade usa encadeamento com rehash incremental (move os baldes aos poucos pra não travar o servidor num resize gigante) — e isso é exatamente análise amortizada (próximo tópico) aplicada, encostando na concorrência da C2. Implementar open addressing aqui é o exercício que faz você entender por que cada escolha existe.

  1. (Fácil) Escreva double hm_load(HMap *h) que devolve o fator de carga (size/cap) e dispare o resize quando passar de 0,7.
  2. (Médio) Robin Hood: ao inserir, se a sua "distância de sondagem" for maior que a do ocupante, troque de lugar com ele e continue inserindo o que foi deslocado. Por que isso reduz a variância (a pior busca fica bem menor)?
  3. (Difícil) Cuckoo hashing: duas tabelas e dois hashes. Cada chave mora num de dois lugares possíveis; ao inserir, se ambos estão ocupados, expulse um e o realoque na outra tabela (pode virar uma corrente). Por que a busca vira O(1) garantido — e o que fazer quando entra em ciclo?

Gabarito

1. double hm_load(HMap *h){ return (double)h->size / h->cap; } — chame no início do hm_put; se > 0.7, hm_resize(h, h->cap*2). (No código acima isso já está como aritmética inteira size*10 >= cap*7 pra evitar ponto flutuante.)

2. Em Robin Hood, ninguém fica "rico" (perto do seu balde ideal) enquanto outro está "pobre" (longe): você equaliza as distâncias trocando. Como a maior distância de sondagem cai, o pior caso de busca encolhe muito — a tabela fica com desempenho mais previsível, mesmo cheia.

3. Na busca você só olha dois lugares (hash1 na tabela 1, hash2 na tabela 2): se não está em nenhum, não existe → O(1) garantido. O insert é que pode "chutar" inquilinos em cadeia; se a corrente passar de um limite (ciclo), você faz rehash com novas funções hash (ou cresce as tabelas) e tenta de novo.

Anki

P: Encadeamento vs open addressing? → R: encadeamento pendura uma lista por balde; open addressing guarda tudo no próprio array e sonda o próximo livre.

P: Por que delete vira tombstone e não EMPTY? → R: EMPTY furaria a cadeia de sondagem e a busca acharia "não existe" erroneamente.

P: O que é fator de carga e por que importa? → R: size/cap; acima de ~0,7 formam-se clusters e as operações degradam pra O(n).

P: A vantagem do cuckoo hashing? → R: busca O(1) no pior caso (só 2 posições possíveis).

P: O que Robin Hood otimiza? → R: a variância — reduz a maior distância de sondagem, deixando o pior caso menor.

Complexidade

Os 🆕 da análise. Os ✅ (Big-O, Ω, Θ, o/ω, runtimes comuns) você já tem. Faltavam os dois mais "manhosos": custo amortizado e espaço.

6 · Amortized Analysis

Análise amortizada é o custo médio por operação ao longo de uma sequência — mesmo que uma operação isolada, de vez em quando, seja cara. Analogia: assinatura anual da academia. Você paga um valorzão uma vez, mas dividido pelos treinos do ano sai barato por treino. Atenção: isso não é "caso médio" (que é probabilístico, depende de sorte na entrada). Amortizado é uma garantia sobre a sequência inteira, sem depender de probabilidade.

Quando usar / quando NÃO usar

USE pra avaliar estruturas com operações esporádicas e caras, mas raras: o push do vetor dinâmico (dobra de vez em quando), o Union-Find com compressão de caminho, a Splay Tree.

NÃO confunda com caso médio. E cuidado: amortizado O(1) não significa que cada operação é O(1) — a cara ainda existe. Em tempo real (jogos, áudio, robótica) esse pico de latência pode ser inaceitável.

ExemploPior caso (1 op)Amortizado
push do vetor dinâmico (dobrando)O(n)O(1)
incrementar contador binárioO(k bits)O(1)
Union-Find (compressão + rank)O(log n)~O(α(n)) ≈ O(1)
rehash incremental da hash tableO(n)O(1)

Três métodos pra provar: agregado (soma o custo de n operações e divide por n), contábil/banqueiro (cobra um "extra" barato em cada op pra pagar a cara depois) e potencial (define uma função Φ que mede "energia acumulada"). O agregado é o mais intuitivo pra começar.

#include <stdio.h>
#include <stdlib.h>

// Prova EMPÍRICA do agregado: faz N pushes e CONTA quantas cópias o crescimento
// fez no total. Vai dar ~N (cada push "paga" ~1 cópia) -> O(1) amortizado.
int main(void) {
    int   *data = NULL;
    size_t size = 0, cap = 0;
    long   copias = 0;            // total de cópias feitas pelos crescimentos
    int    N = 1000000;

    for (int i = 0; i < N; i++) {
        if (size == cap) {                       // encheu: hora de crescer
            size_t nova = (cap == 0) ? 1 : cap * 2;
            int *novo = malloc(nova * sizeof(int));
            for (size_t k = 0; k < size; k++) {  // copia manual SÓ p/ contar
                novo[k] = data[k];
                copias++;
            }
            free(data); data = novo; cap = nova;
        }
        data[size++] = i;                        // o push barato (a maioria das vezes)
    }
    printf("N pushes  = %d\n", N);
    printf("copias    = %ld\n", copias);
    printf("por push  = %.2f  (constante -> O(1) amortizado)\n", (double)copias / N);
    free(data);
    return 0;
}

⚠ Erro nº1: confundir amortizado com caso médio (e achar que "cada" op é barata)

Caso médio depende da distribuição da entrada (probabilidade). Amortizado é garantido sobre a sequência, sem sorte nenhuma — são coisas diferentes. E o pega-ratão: "O(1) amortizado" não quer dizer que toda operação é O(1). Aquele push que dobra ainda é O(n) naquele instante — num sistema sensível a latência, esse pico importa (é por isso que existe o rehash incremental).

Direto no projeto (mini-Redis)

Tudo que "cresce sozinho" no seu banco é amortizado: o buffer de comandos e a sds (C0/C3) e, principalmente, o rehash da tabela hash. O Redis faz o rehash incremental justamente pra transformar um O(n) gigante (que travaria o servidor) em vários passinhos O(1) amortizados — análise amortizada na prática, encostando na concorrência da C2.

  1. (Fácil) Pelo método agregado, mostre que n pushes num vetor que dobra custam O(n) no total. (Dica: some 1 + 2 + 4 + … + n/2.)
  2. (Médio) Contador binário: incrementar um número binário de 0 até n. Mostre que o número total de bits virados é O(n) (não O(n·log n)), logo O(1) amortizado por incremento.
  3. (Difícil) Método do potencial: defina Φ = 2·size − capacity pro vetor dinâmico e mostre que o custo amortizado do push (real + ΔΦ) é constante.

Gabarito

1. A soma das cópias é a série geométrica 1 + 2 + 4 + … + n/2 = n − 1 < n. Some os n pushes baratos (n) e dá < 2n = O(n) total → O(1) por push.

2. O bit 0 vira em todo incremento (n vezes); o bit 1 vira a cada 2 (n/2); o bit 2 a cada 4 (n/4)… Total = n + n/2 + n/4 + … < 2n = O(n). Dividido por n incrementos → O(1) amortizado.

3. Num push sem crescer: custo real 1, ΔΦ = +2 (size sobe 1) → amortizado = 1 + 2 = 3. No push que dobra (size = capacity = m): custo real ≈ m+1, mas Φ cai de ≈ m pra ≈ 2 (a folga nova "guarda crédito"), ΔΦ ≈ 2 − m, então amortizado ≈ (m+1) + (2 − m) = 3 = O(1). Φ "paga" as cópias.

Anki

P: Amortizado vs caso médio? → R: amortizado é garantia sobre a sequência (sem probabilidade); caso médio depende da distribuição da entrada.

P: Os três métodos de análise amortizada? → R: agregado, contábil (banqueiro) e potencial.

P: "O(1) amortizado" garante que toda op é O(1)? → R: não — a operação cara ainda existe; só o custo médio da sequência é O(1).

P: Por que o rehash do Redis é incremental? → R: pra diluir um O(n) que travaria o servidor em passos O(1) amortizados.

P: Total de cópias em n pushes dobrando? → R: < n (série geométrica), logo O(1) por push.

7 · Space Complexity a fundo

Complexidade de espaço é quanta memória extra um algoritmo usa em função do tamanho da entrada. A pegadinha é separar duas coisas: o espaço da própria entrada (que você recebe pronta) e o espaço auxiliar (o que você aloca a mais pra resolver). Quando alguém diz "esse algoritmo é O(1) de espaço", está falando do auxiliar. Analogia: cozinhar — os ingredientes na bancada são a entrada; as tigelas e panelas extras que você suja são o espaço auxiliar.

Quando importa

Quando memória é o gargalo: embarcados, big data, e código cache-sensível. E sempre que houver recursão profunda — cada chamada empilha um frame, então recursão tem custo de espaço na pilha que muita gente esquece. Quase sempre existe um trade-off tempo × espaço: memoização gasta memória pra ganhar tempo, e vice-versa.

// RECURSIVO: parece inocente, mas cada chamada empilha um frame.
// Espaço auxiliar = O(n) na PILHA (n frames abertos antes de fechar o 1º).
long soma_rec(int n) {
    if (n == 0) return 0;            // caso base
    return n + soma_rec(n - 1);      // abre outro frame... e outro... e outro
}

// ITERATIVO: um único frame, uma variável. Espaço auxiliar = O(1).
long soma_iter(int n) {
    long s = 0;                      // o ÚNICO espaço extra
    for (int i = 1; i <= n; i++) s += i;
    return s;                        // mesmo resultado, sem risco de stack overflow
}

// Inverter um array IN-PLACE: O(1) de espaço (troca nas pontas, sem cópia).
void inverte(int *v, size_t n) {
    size_t i = 0, j = n - 1;
    while (i < j) {                   // caminha das pontas pro meio
        int t = v[i]; v[i] = v[j]; v[j] = t;  // troca; só 1 var temporária
        i++; j--;
    }
}

⚠ Erro nº1: esquecer a pilha de recursão (e contar a entrada como auxiliar)

Dizer que um algoritmo recursivo é "O(1) de espaço" porque "não aloco nada" é o erro clássico — a pilha de chamadas é espaço, e uma recursão de profundidade n é O(n) de espaço (e pode estourar a pilha). O outro deslize é contar a entrada como auxiliar: se o problema já te entrega o array, esse array não conta no espaço extra — só conta o que você aloca além dele.

Direto no projeto (mini-Redis)

Memória é caro num banco em RAM. Nas travessias dos índices em árvore (C4/C8), prefira versão iterativa com pilha explícita a recursão funda — você controla o limite e não arrisca estourar a pilha do SO com uma árvore degenerada. E o despejo (C1) é o trade-off tempo×espaço em pessoa: você "gasta" estrutura extra (LRU/LFU) pra economizar a memória total do store.

  1. (Fácil) Qual o espaço auxiliar de inverter uma string in-place? E de checar se ela é palíndromo?
  2. (Médio) Reescreva o Fibonacci pra rodar em O(1) de espaço (sem recursão, sem array — só duas variáveis).
  3. (Difícil) Converta uma travessia in-order recursiva (O(h) de pilha) numa iterativa com pilha explícita (mesma O(h), mas sob seu controle). Depois pesquise o Morris traversal e diga por que ele consegue O(1) de espaço.

Gabarito

1. Ambos O(1): você só usa dois índices (e uma temporária pra trocar). A string em si é a entrada — não conta como auxiliar.

2. long fib(int n){ long a=0,b=1; for(int i=0;i<n;i++){ long t=a+b; a=b; b=t; } return a; } — guarda só os dois últimos termos → O(1) espaço, O(n) tempo.

3. Use uma pilha explícita: empurre indo todo à esquerda; ao desempilhar, visite o nó e vá pra subárvore direita. A profundidade máxima da pilha é a altura h → O(h), igual à recursiva, mas sem usar a pilha do SO. O Morris traversal atinge O(1) "tomando emprestados" os ponteiros nulos da árvore (threads temporários) pra voltar sem pilha — restaurando a árvore no fim.

Anki

P: Espaço da entrada vs espaço auxiliar? → R: entrada é o que você recebe pronto; auxiliar é o que você aloca a mais. "O(1) de espaço" se refere ao auxiliar.

P: Por que recursão tem custo de espaço? → R: cada chamada empilha um frame; profundidade n → O(n) de pilha (e risco de stack overflow).

P: Espaço auxiliar do Merge Sort e do Quick Sort? → R: Merge O(n) (array do merge); Quick O(log n) médio / O(n) pior (pilha).

P: Como deixar o Fibonacci O(1) de espaço? → R: iterativo guardando só os dois últimos termos.

P: O que o Morris traversal alcança? → R: travessia in-order em O(1) de espaço, usando ponteiros nulos como threads temporários.

Árvores

Os 🆕 das árvores. Os ✅ (Tree, Binary Tree, travessias, BST, full/complete/perfect/balanced) você já tem. Começamos pelas duas autobalanceadas — as que garantem altura O(log n) e nunca degeneram numa "lista torta".

6 · Árvore AVL

Uma AVL é uma BST que se reequilibra sozinha a cada inserção/remoção, garantindo que a altura fique sempre em O(log n). O segredo é o fator de balanço de cada nó (altura da subárvore esquerda − altura da direita): ele só pode ser −1, 0 ou +1. Passou disso, a árvore faz uma rotação e se ajeita. Analogia: uma estante de livros que, toda vez que pende demais pra um lado, você reorganiza pra ela não tombar — em vez de virar uma "torre de Pisa" (a BST degenerada vira uma lista O(n)).

Quando usar / quando NÃO usar

USE quando buscas dominam e você precisa de lookup previsível O(log n) sempre — a AVL fica a árvore mais "rasa" possível.

NÃO use quando inserir/remover é o mais frequente (a AVL roda mais que a Rubro-Negra pra manter o equilíbrio apertado) ou quando os dados chegam bem embaralhados (uma BST simples já fica boa na média e é mais barata).

OperaçãoTempo (Big-O)Espaço
BuscarO(log n) garantidoO(1) iterativo
InserirO(log n)O(log n) pilha
RemoverO(log n)O(log n) pilha
MemóriaO(n)+1 inteiro (altura) por nó

O ganho sobre a BST comum é no pior caso: a BST pode virar uma lista (insira 1,2,3,4,5… em ordem → altura n → busca O(n)). A AVL garante O(log n) mesmo nesse cenário. São 4 casos de desequilíbrio, resolvidos com 1 ou 2 rotações: Esq-Esq (1 rotação à direita), Dir-Dir (1 à esquerda), Esq-Dir e Dir-Esq (rotação dupla).

#include <stdlib.h>

typedef struct Node {
    int          key, height;       // guardamos a altura no próprio nó
    struct Node *left, *right;
} Node;

static int h(Node *n)   { return n ? n->height : 0; }              // altura de NULL = 0
static int mx(int a,int b){ return a > b ? a : b; }
static int bf(Node *n)  { return n ? h(n->left) - h(n->right) : 0; } // fator de balanço

static Node* novo(int key) {
    Node *n = malloc(sizeof(Node));
    n->key = key; n->height = 1; n->left = n->right = NULL;
    return n;
}

// Rotação à DIREITA (conserta o caso Esquerda-Esquerda).
static Node* rot_right(Node *y) {
    Node *x = y->left, *t = x->right;
    x->right = y; y->left = t;                    // gira: x sobe, y desce
    y->height = 1 + mx(h(y->left), h(y->right));  // atualiza y PRIMEIRO (virou filho)
    x->height = 1 + mx(h(x->left), h(x->right));  // depois x (virou pai)
    return x;                                    // x é a nova raiz da subárvore
}

// Rotação à ESQUERDA: espelho exato (troca left<->right).
static Node* rot_left(Node *x) {
    Node *y = x->right, *t = y->left;
    y->left = x; x->right = t;
    x->height = 1 + mx(h(x->left), h(x->right));
    y->height = 1 + mx(h(y->left), h(y->right));
    return y;
}

// Insere e, na VOLTA da recursão, reequilibra cada nó no caminho.
Node* avl_insert(Node *n, int key) {
    if (!n) return novo(key);                    // achou o lugar: cria a folha
    if      (key < n->key) n->left  = avl_insert(n->left,  key);
    else if (key > n->key) n->right = avl_insert(n->right, key);
    else    return n;                            // chave repetida: ignora

    n->height = 1 + mx(h(n->left), h(n->right));  // recalcula a altura subindo
    int b = bf(n);                               // desbalanceou?

    if (b > 1  && key < n->left->key)  return rot_right(n);  // Esq-Esq
    if (b < -1 && key > n->right->key) return rot_left(n);   // Dir-Dir
    if (b > 1  && key > n->left->key)  {           // Esq-Dir (rotação dupla)
        n->left = rot_left(n->left); return rot_right(n);
    }
    if (b < -1 && key < n->right->key) {           // Dir-Esq (rotação dupla)
        n->right = rot_right(n->right); return rot_left(n);
    }
    return n;                                     // já estava balanceado
}

⚠ Erro nº1: esquecer de atualizar as alturas (na ordem certa) após rotacionar

Depois de girar, o nó que desceu tem que ter a altura recalculada antes do que subiu (filho antes do pai) — inverter a ordem dá altura errada e a árvore vai desbalanceando em silêncio. O outro tropeço é confundir os casos duplos: Esq-Dir é uma rotação à esquerda no filho esquerdo e depois à direita na raiz (e o Dir-Esq é o espelho). Decore: o "joelho dobrado" (zig-zag) precisa de duas rotações pra virar "linha reta".

Direto no projeto (mini-Redis)

Toda estrutura ordenada com busca rápida cai aqui. No capstone, é a base teórica dos índices secundários (Camada C4) e do Sorted Set (C8) — manter chaves em ordem pra responder ZRANGE/range queries em O(log n). O Redis real usa skip list pro ZSET (próximo lote), mas a AVL é a versão "livro-texto" do mesmo papel, e a B-Tree (lote de árvores parte 2) é a versão pra disco.

  1. (Fácil) Escreva uma função que, dado um nó, diga em qual dos 4 casos (EE, DD, ED, DE) ele está — ou que está balanceado.
  2. (Médio) Dado o rot_right, prove que o rot_left é o espelho exato (escreva-o sem olhar e confira).
  3. (Difícil) Implemente avl_delete: remova como numa BST (caso da folha, do nó com 1 filho e do nó com 2 filhos via sucessor in-order) e reequilibre na volta, igual ao insert.

Gabarito

1. Calcule b = bf(n). Se b>1: é EE se bf(n->left)>=0, senão ED. Se b<-1: é DD se bf(n->right)<=0, senão DE. |b|<=1 → balanceado. (Olhar o filho diz se o desequilíbrio é "reto" ou "joelho".)

2. Troque sistematicamente left↔right no rot_right: pega y = x->right, move y->left pra x->right, faz y->left = x. É exatamente o código acima.

3. O esqueleto é o mesmo do insert: desça recursivo até achar a chave; nos 3 casos de remoção, no de 2 filhos copie o menor da subárvore direita (sucessor) e remova-o lá embaixo; na volta, recalcule height e aplique as mesmas 4 checagens de rotação — só que aqui o desequilíbrio pode aparecer mesmo "do outro lado", então use bf dos filhos pra decidir o caso (não dá pra usar a "key inserida").

Anki

P: O que a AVL garante e como? → R: altura O(log n), mantendo o fator de balanço de todo nó em {−1,0,+1} via rotações.

P: Os 4 casos de desequilíbrio? → R: Esq-Esq, Dir-Dir (1 rotação) e Esq-Dir, Dir-Esq (rotação dupla).

P: Por que a BST comum pode ser O(n)? → R: inserções em ordem crescente a degeneram numa lista; a AVL impede isso.

P: Ordem de atualizar as alturas após rotação? → R: filho (quem desceu) antes do pai (quem subiu).

P: AVL vs Rubro-Negra, em uma frase? → R: AVL é mais rasa (busca melhor); RB roda menos (escrita melhor).

7 · Árvore Rubro-Negra (Red-Black)

Outra BST autobalanceada — mas em vez de medir altura exata, ela segue regras de cor (cada nó é vermelho ou preto). Isso deixa o balanceamento mais "frouxo" que a AVL (a árvore não fica tão perfeitamente rasa), e em troca ela faz menos rotações nas inserções e remoções. Por isso é o cavalo de batalha de bibliotecas inteiras: std::map/std::set do C++, TreeMap do Java, o escalonador CFS do kernel Linux. Analogia: regras de trânsito por cor — você não mede a distância exata de tudo, segue 5 regrinhas de cor que mantêm o sistema "bom o suficiente" e estável.

Quando usar / quando NÃO usar

USE quando inserir/remover é frequente e você quer um balanceamento "bom o suficiente" com poucas rotações por escrita — é a escolha padrão de mapas/sets ordenados nas linguagens.

NÃO use quando a leitura é absolutamente dominante e cada nível conta (a AVL fica um tiquinho mais rasa), ou quando você não precisa de ordenação (uma hash table dá O(1) e é bem mais simples). Implementar RB certo é notoriamente chato — não reinvente se a lib já tem.

OperaçãoTempo (Big-O)Observação
Buscar / Inserir / RemoverO(log n) garantidoaltura ≤ 2·log₂(n+1)
Rotações por inserção≤ 2menos que a AVL no pior caso

As 5 propriedades que toda RB mantém: (1) todo nó é vermelho ou preto; (2) a raiz é preta; (3) toda folha NIL é preta; (4) filho de nó vermelho é preto (não há dois vermelhos seguidos); (5) todo caminho da raiz até as folhas tem o mesmo número de nós pretos (a "altura-preta"). São essas 5 regras que forçam a árvore a ficar aproximadamente balanceada.

#include <stdlib.h>

typedef enum { RED, BLACK } Color;
typedef struct Node {
    int           key;
    Color         color;
    struct Node  *left, *right, *parent;
} Node;

typedef struct {
    Node *root;
    Node *nil;   // SENTINELA: uma folha preta única que substitui todo NULL
} RBTree;

void rb_init(RBTree *t) {
    t->nil = malloc(sizeof(Node));
    t->nil->color = BLACK;                       // a sentinela é sempre preta
    t->nil->left = t->nil->right = t->nil->parent = t->nil;
    t->root = t->nil;
}

// Rotação à esquerda em torno de x (o filho direito, y, sobe).
static void rot_left(RBTree *t, Node *x) {
    Node *y = x->right;
    x->right = y->left;                          // a subárvore esq. de y vira dir. de x
    if (y->left != t->nil) y->left->parent = x;
    y->parent = x->parent;                       // liga y ao pai de x
    if      (x->parent == t->nil)   t->root = y;
    else if (x == x->parent->left)  x->parent->left = y;
    else                           x->parent->right = y;
    y->left = x; x->parent = y;                  // x desce pra esquerda de y
}

// Rotação à direita: espelho exato (left<->right).
static void rot_right(RBTree *t, Node *x) {
    Node *y = x->left;
    x->left = y->right;
    if (y->right != t->nil) y->right->parent = x;
    y->parent = x->parent;
    if      (x->parent == t->nil)    t->root = y;
    else if (x == x->parent->right)  x->parent->right = y;
    else                            x->parent->left = y;
    y->right = x; x->parent = y;
}

// Conserta as 5 propriedades depois de inserir z (que entra VERMELHO).
static void rb_fix(RBTree *t, Node *z) {
    while (z->parent->color == RED) {            // só há problema com pai vermelho
        if (z->parent == z->parent->parent->left) {
            Node *tio = z->parent->parent->right;
            if (tio->color == RED) {             // CASO 1: tio vermelho -> só recolore
                z->parent->color = BLACK; tio->color = BLACK;
                z->parent->parent->color = RED;
                z = z->parent->parent;           // sobe e repete
            } else {
                if (z == z->parent->right) {     // CASO 2: "joelho" -> vira linha
                    z = z->parent; rot_left(t, z);
                }
                z->parent->color = BLACK;        // CASO 3: linha -> recolore + roda
                z->parent->parent->color = RED;
                rot_right(t, z->parent->parent);
            }
        } else {                                // espelho (pai é filho direito)
            Node *tio = z->parent->parent->left;
            if (tio->color == RED) {
                z->parent->color = BLACK; tio->color = BLACK;
                z->parent->parent->color = RED;
                z = z->parent->parent;
            } else {
                if (z == z->parent->left) { z = z->parent; rot_right(t, z); }
                z->parent->color = BLACK;
                z->parent->parent->color = RED;
                rot_left(t, z->parent->parent);
            }
        }
    }
    t->root->color = BLACK;                      // regra de ouro: raiz SEMPRE preta
}

void rb_insert(RBTree *t, int key) {
    Node *z = malloc(sizeof(Node));
    z->key = key; z->color = RED;                // todo nó novo entra vermelho
    z->left = z->right = t->nil;
    Node *y = t->nil, *x = t->root;              // BST normal pra achar o lugar
    while (x != t->nil) { y = x; x = (key < x->key) ? x->left : x->right; }
    z->parent = y;
    if      (y == t->nil)     t->root = z;
    else if (key < y->key)    y->left = z;
    else                     y->right = z;
    rb_fix(t, z);                               // reequilibra por cor/rotação
}

⚠ Erro nº1: usar NULL em vez da sentinela (e esquecer que a raiz é preta)

O rb_fix lê a cor do tio e do avô sem checar se existem. Se você usar NULL pras folhas, vai dar segfault ao ler NULL->color. A solução clássica é a sentinela nil: um único nó preto que faz papel de todas as folhas — assim você nunca lê um ponteiro nulo. O segundo erro é terminar o fixup sem forçar root->color = BLACK (o Caso 1 pode ter pintado a raiz de vermelho).

Direto no projeto (mini-Redis)

Mesmo papel da AVL — estrutura ordenada pra índices secundários (C4) e Sorted Set (C8) — só que otimizada pra escrita. É exatamente por que std::map e TreeMap a escolhem: muitas inserções/remoções com balanceamento barato. Bom contraponto pro skip list (que o Redis realmente usa no ZSET) no próximo lote.

  1. (Fácil) Liste as 5 propriedades de memória e explique, em uma frase, por que elas forçam altura ≤ 2·log₂(n+1).
  2. (Médio) No código acima eu escrevi rot_right como espelho de rot_left. Cubra-o e reescreva do zero, só trocando left↔right; confira.
  3. (Difícil) Pesquise e implemente o rb_delete com seu rb_delete_fixup (os 4 casos do irmão). É o trecho mais difícil de toda a estrutura de dados clássica — vale como projeto à parte.

Gabarito

1. Como (4) proíbe dois vermelhos seguidos e (5) exige a mesma quantidade de pretos em todo caminho, o caminho mais longo (que alterna preto-vermelho) tem no máximo o dobro do mais curto (só pretos). Logo a altura é ≤ 2× a altura-preta ≈ 2·log₂(n+1) → O(log n).

2. Pega y = x->left; move y->right pra x->left; religa o pai checando x == x->parent->right; faz y->right = x. É o que está no código.

3. A remoção segue a BST (com a "transplante" de subárvores) e, se o nó removido/movido era preto, você cria um "preto a mais" que precisa ser empurrado pra cima pelo fixup, tratando os 4 casos do irmão (vermelho; preto com filhos pretos; preto com filho perto vermelho; preto com filho longe vermelho). Use a referência do CLRS — e teste com bateria de inserções/remoções aleatórias verificando as 5 propriedades a cada passo.

Anki

P: A ideia central da Rubro-Negra? → R: balancear por regras de cor (não por altura exata), trocando "árvore mais rasa" por "menos rotações na escrita".

P: As 5 propriedades, resumidas? → R: nó é R/B; raiz preta; folhas NIL pretas; sem dois vermelhos seguidos; mesma altura-preta em todo caminho.

P: Por que usar uma sentinela nil? → R: pra nunca ler NULL->color no fixup (evita segfault) e simplificar os casos.

P: De que cor entra um nó novo, e por quê? → R: vermelho — não viola a altura-preta; no pior caso vira só "dois vermelhos seguidos", que o fixup conserta.

3 · Artigos — a, an, the

  1. a = um/uma, antes de som de consoante: a car, a book, a university (“iu”, som de consoante).
  2. an = um/uma, antes de som de vogal: an apple, an hour (o “h” é mudo).
  3. the = o/a/os/as, quando é algo específico: the car I bought (o carro que comprei).

4 · Plural dos substantivos

  1. Regra geral: +s → car → cars, book → books.
  2. Depois de s, x, ch, sh: +es → box → boxes, watch → watches.
  3. Termina em consoante + y: y → ies → city → cities, baby → babies.
  4. Irregulares (decore): man → men, woman → women, child → children, person → people, foot → feet.

⚠ people é plural

“People” já é o plural de “person”. Então é people are, nunca “people is”. E não existe “peoples” no sentido de pessoas.

5 · Present Simple — rotinas e fatos

Usa pra hábitos, rotinas e verdades (“eu trabalho”, “ela mora”, “a água ferve a 100°”). É o tempo mais usado.

Eles estudam inglês todo dia.

A regra do -s na 3ª pessoa

Com he / she / it, o verbo ganha -s: He works, She lives. Esquecer esse “s” é o erro mais comum de todos — fique atento.

Negativo e pergunta usam o auxiliar do (e does na 3ª pessoa). Repare: o “s” migra pro does e o verbo volta ao normal.

15 · Present Perfect — o passado que toca o presente

Esse é o tempo que mais confunde brasileiro, porque não tem tradução exata. Fórmula: have/has + particípio (a 3ª forma do verbo). Liga uma ação do passado ao agora — sem dizer quando exatamente.

I have finished the report.
Eu terminei o relatório. (e está pronto agora)
She has lived here for ten years.
Ela mora aqui há dez anos. (e ainda mora)
Have you ever traveled abroad?
Você já viajou pro exterior? (experiência de vida)

for vs since

for = um período (for two years = por dois anos). since = o ponto de início (since 2020 = desde 2020). Companheiros úteis: already (já), yet (ainda — em negativas/perguntas), just (acabou de).

⚠ Present Perfect vs Past Simple

Use Past Simple quando diz quando (I ate at 8pm). Use Present Perfect quando o tempo é indefinido e o resultado importa agora (I have eaten = já comi, não estou com fome).

16 · Present Perfect Continuous — duração que continua

Fórmula: have/has been + verbo-ing. Enfatiza quanto tempo algo vem acontecendo (e geralmente ainda acontece).

I have been studying for three hours.
Estou estudando há três horas.
It has been raining all day.
Está chovendo o dia todo.

17 · Past Continuous — o que estava rolando

Fórmula: was/were + verbo-ing. Ação em andamento no passado, geralmente interrompida por outra (no Past Simple).

I was sleeping when the phone rang.
Eu estava dormindo quando o telefone tocou.
They were working while I was cooking.
Eles estavam trabalhando enquanto eu cozinhava.

18 · Past Perfect — o passado do passado

Fórmula: had + particípio. Marca algo que aconteceu antes de outro momento no passado.

She had never seen snow before that trip.

21 · Gerúndio (-ing) vs Infinitivo (to)

Depois de certos verbos vem -ing; depois de outros, to + verbo. Não tem regra mágica — os principais se decoram com o uso.

  1. + -ing: like, love, enjoy, hate, finish, avoid, e depois de qualquer preposição.
  2. + to: want, need, decide, hope, would like, learn.

23 · Advérbios e frequência

Advérbio diz como algo acontece. Formação comum: adjetivo + -ly (quick → quickly). Irregulares: good → well, fast → fast.

Advérbios de frequência (always, usually, often, sometimes, rarely, never) vêm antes do verbo principal, mas depois do TO BE.

Quando o foco vai pra quem sofre a ação, não pra quem faz. Fórmula: be (no tempo certo) + particípio.

Em vários tempos

Só muda o be: is made (presente), was made (passado), has been made (present perfect), will be made (futuro).

28 · Discurso indireto (reported speech)

Quando você conta o que alguém disse. Os tempos “andam um passo pra trás” (backshift): presente vira passado, will vira would, can vira could.

Direct: "I am tired."
Direto: “Estou cansado.”
Reported: He said he was tired.

Reported: She said she would call me.

29 · Wish / If only — desejos e arrependimentos

Pra falar do que você gostaria que fosse diferente. Repare que o tempo “recua”: pra um desejo no presente, usa-se passado; pra arrependimento do passado, past perfect.

I wish I had more time.

I wish I had studied harder.
Eu queria ter estudado mais. (arrependimento)

30 · Modais avançados — dedução e “modal perfect”

  1. Dedução: must be (deve ser — quase certeza), can't be (não pode ser), might/could be (talvez).
  2. Modal + have + particípio (sobre o passado): should have done (deveria ter feito), must have done (deve ter feito), could have done (poderia ter feito).
You must be exhausted after that.
Você deve estar exausto depois disso.
I should have called you yesterday.
Eu deveria ter te ligado ontem.

31 · Phrasal verbs — como funcionam

São verbo + partícula (preposição/advérbio) que, juntos, mudam o sentido. look = olhar, mas look for = procurar, look after = cuidar de. Não dá pra traduzir ao pé da letra — aprende-se pelo uso.

Alguns do dia a dia: get up (levantar), give up (desistir), find out (descobrir), turn on/off (ligar/desligar), come back (voltar), look for (procurar).

Separáveis

Muitos aceitam o objeto no meio: turn the light off = turn off the light. Com pronome, é obrigatório no meio: turn it off (nunca “turn off it”).

Parte 3 · depois do núcleo

Nível craque mundial

O roadmap inteiro já faz de vocês ótimos profissionais. Esta parte é o que separa “muito bom” de elite mundial — opcional, pra fazer depois (ou em paralelo) do núcleo, conforme o interesse de cada um.

A real sobre “ser craque”

Ninguém vira elite vendo mais vídeo. Vira construindo coisas difíceis, lendo código dos grandes e indo fundo num assunto. O capstone de vocês já é metade disso. O resto é profundidade e gosto por entender o “por quê” embaixo de cada camada.

1 · Algoritmos de elite

  • Programação dinâmica avançada (DP em árvore, bitmask, em intervalos) e fluxo máximo (Dinic, min-cost-max-flow).
  • Algoritmos de string de verdade: Suffix Array/Automaton, Aho-Corasick, Z-function.
  • Geometria computacional (convex hull, sweep line).
  • Treino: Codeforces / competitive programming — é academia pesada pra raciocínio algorítmico.

2 · Matemática de verdade

É o que destrava ML, criptografia e análise séria de algoritmos: matemática discreta (lógica, combinatória, grafos), álgebra linear (base de toda IA), teoria dos números (criptografia) e probabilidade.

3 · Sistemas a fundo

  • Como um compilador funciona (lexer, parser, geração de código) — escreva um pequeno.
  • Internals de SO: escreva um “toy kernel” ou um shell; entenda paginação e escalonamento por dentro.
  • Internals de banco: B+Tree, LSM-Tree, MVCC, WAL — exatamente o que o capstone toca.
  • Sistemas distribuídos: consenso (Raft, Paxos), CAP/PACELC na prática, relógios lógicos.

4 · Performance e concorrência (mechanical sympathy)

  • Programação cache-aware, SIMD/vetorização, profiling com perf.
  • Concorrência avançada: estruturas lock-free, atomics, memory ordering, event loop (epoll/io_uring).

5 · Qualidade e meta-habilidades

  • Testes property-based, fuzzing, e uma pitada de métodos formais (TLA+).
  • Ler papers (o do Raft, o do Dynamo, o do MapReduce) e ler código de projetos grandes (Redis, SQLite, Linux).
  • Contribuir pra open source e escrever/ensinar — ensinar é o teste final de domínio.

Livros que valem a estante (recomendação, não cópia)

Designing Data-Intensive Applications (Kleppmann) · Computer Systems: A Programmer's Perspective (Bryant & O'Hallaron) · The Algorithm Design Manual (Skiena) · Operating Systems: Three Easy Pieces (grátis online). São os clássicos que aparecem na estante de quase todo engenheiro sênior.

Como levar o capstone ao nível elite

Quando o banco de dados de vocês estiver pronto, estes “stretch goals” o colocam em outro patamar — e rendem os melhores posts de todos: (1) consenso com Raft (réplicas que concordam mesmo com falha); (2) storage em LSM-Tree (como o RocksDB); (3) rede com io_uring/epoll (milhares de conexões); (4) hash table lock-free; (5) fuzzing do parser do protocolo. Cada um destes é assunto de entrevista de empresa top.

§Sua trilha de mentor

Sua preparação é diferente da deles — você já é avançado.

  • Veja sempre um módulo na frente, em 1.5x–2x. Você não está aprendendo o conteúdo; está caçando como o professor explica.
  • Colete analogias. Tenha 2–3 formas de explicar cada conceito difícil. Eles vão perguntar a mesma coisa de cinco jeitos.
  • Sobre-prepare ponteiros e memória. É o muro onde a maioria trava. Tenha pronto: endereço = "número da casa", * = "abrir a casa", & = "pegar o endereço".
  • Reimplemente cada estrutura antes de ensinar, pra codar ao vivo sem gaguejar.
  • Na Fase 4 (Mario), estude de verdade, não em 2x. As provas e análises fecham aquele gap de confundir posição física no array com rank lógico ordenado.
  • Ensinar é o seu teste de maestria. Se não consegue explicar simples, não dominou. Ensinar consolida mais que qualquer revisão.
